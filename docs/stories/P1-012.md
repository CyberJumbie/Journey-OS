# P1-012: Dual Embedding Service (Voyage AI + OpenAI)
**Epic:** 1.2 — Single Course Ingestion
**Points:** 5 | **Depends:** P1-011 (chunks classified and stored)
**Context packet:** docs/context-packets/CP-EPIC-1.2.md
**Solution doc:** docs/solutions/SOL-008-dual-embedding-provider.md

**As a** system  
**I want** vector embeddings from both Voyage AI and OpenAI stored per chunk  
**So that** we can compare retrieval quality over 6 months before committing to one provider

## Why Two Providers

Voyage AI (voyage-large-2, 1024-dim) and OpenAI (text-embedding-3-small, 1536-dim) have incompatible dimensions — they cannot share a single vector(N) column. We store both at ingest time so switching the search provider requires only a config change, no re-ingestion.

## Acceptance Criteria

- content_chunk_embeddings has two nullable vector columns: voyage_embedding vector(1024) and openai_embedding vector(1536)
- Two HNSW indexes — one per column (separate ops classes)
- IEmbeddingProvider interface: { name, model, dimensions, embed(texts) }
- VoyageEmbeddingProvider and OpenAIEmbeddingProvider both implement it
- EmbeddingProviderFactory.getIngestProviders(config) — controlled by EMBEDDING_PROVIDERS env var
- EmbeddingProviderFactory.getSearchProvider(config) — controlled by EMBEDDING_SEARCH_PROVIDER env var
- EmbedderService.embedChunks() runs ALL ingest providers sequentially (not parallel)
- EmbedderService.searchChunks() uses search provider + correct RPC function
- Voyage batch limit: 128 texts max; OpenAI batch limit: 100 texts max
- Supabase RPC functions: search_chunks_voyage(vector(1024)...) and search_chunks_openai(vector(1536)...)

## Smoke Test

```bash
# Both columns populated after ingestion
psql $SUPABASE_DB_URL -c "
  SELECT count(*) total, count(voyage_embedding) voyage, count(openai_embedding) openai
  FROM content_chunk_embeddings;"
# Expected: all three counts equal

# Compare results for same query
curl "localhost:3001/api/v1/search?q=atherosclerosis&courseId=medi-531&provider=voyage"
curl "localhost:3001/api/v1/search?q=atherosclerosis&courseId=medi-531&provider=openai"
# Both return results — may differ in ordering (that's the point)
```

## Failure Modes (see SOL-008 for full details)
1. One column all NULLs → provider API key missing
2. Dimension mismatch → factory must return provider matching the column being queried
3. Rate limits → run providers sequentially, add exponential backoff
4. Backfill needed → POST /api/v1/admin/re-embed?provider=openai for existing chunks
